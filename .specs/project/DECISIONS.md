## 2026-09-08 (later) — First real GitHub Actions run of gates.yml: 5 bugs found+fixed, GHCR live, branch protection blocked by plan
User asked to apply the two remaining pendências (branch protection + product-repo rollout) now that the earlier bugs were fixed. Before touching branch protection, pushed the Gate Hardening commits to `origin/main` for the first time ever (they'd only existed locally until now) — which meant `.github/workflows/gates.yml` ran for real on GitHub Actions for the first time in this initiative's history. It failed, repeatedly, each time on a genuinely new real bug — none of them guessed, all found via reading actual run logs (never trusting a green/red summary without checking):
1. `hashFiles()` used in a JOB-level `if:` — only legal at STEP level (confirmed via `actionlint`, which yamllint can't check). Fixed: moved to step-level guards on every affected step (also incidentally fixes a real branch-protection risk: a job-level `if:`-false job never runs, so a required check depending on it would hang forever).
2. `.harness-sandbox/docker/Dockerfile.sandbox` didn't exist in `agents-harness` — that path only exists in TARGET projects after `install.sh` runs; the template source repo itself never had it. Fixed with a symlink (`.harness-sandbox/docker -> ../docker`), not a physical copy — single source of truth, zero drift risk.
3. Every `docker run ... harness-sandbox:ci bash <script>` line actually executed `/bin/bash bash <script>` (ENTRYPOINT is already `/bin/bash`) — bash treats "bash" as the script name, searches $PATH, finds itself, fails with "cannot execute binary file". Invisible until now because `sandbox-run.sh` (local usage) never passes a command, just opens an interactive shell. Fixed by dropping the redundant leading `bash`/`bash -c`→`-c` everywhere. Reproduced and confirmed the exact fix with plain bash, no Docker needed.
4. `skills/...` didn't exist at `agents-harness`'s root — same root cause as #2 (`agents-harness` keeps its real skills under `claude/skills/`, never ran `install.sh` on itself). Fixed with a second symlink (`skills -> claude/skills`).
5. `ghcr.io/${{ github.repository_owner }}/...` produced `ghcr.io/rastaFul/...` — GHCR rejects non-lowercase repo names, and GitHub Actions' expression language has no case-folding function. Fixed with a real shell step (`tr '[:upper:]' '[:lower:]'`) feeding a step output used in the tag instead.

Result: full green run (`id 34292146125`, all 7 jobs including `publish-image`) confirmed via `gh api`, not the task notification. Multi-arch image genuinely pushed to GHCR — confirmed via the build-push-action log itself (manifest list digest `sha256:ed708d...`, two per-arch manifests + attestations, `pushing manifest ... done`), not just a green checkmark.

**Branch protection: blocked by a real GitHub plan limitation, not a bug.** Both the classic branch-protection API and the newer rulesets API return `403 "Upgrade to GitHub Pro or make this repository public to enable this feature."` for private repos on a free personal plan — tested live against `agents-harness` itself (the lowest-risk repo, per the runbook's own suggested order), not assumed. This blocks EVERY private repo in scope (agents-harness, artists-booking, microgrow, rastafinancas, vetcare, infra-platform) equally. Two real options exist (upgrade to Pro, or make a given repo public) — neither decided here, this is a business/visibility decision for the user, not a technical one for the agent to make. `docs/runbooks/branch-protection.md` updated with this finding and the confirmed real job-context names (from the actual green run) so it's ready to execute the moment either option is chosen.

**Product-repo rollout:** not started. Given the scale (5 repos, each potentially in a different state — existing CI, existing `package.json`, etc.) and that this is explicitly new scope beyond the original Gate Hardening SPEC.md, asked the user to either pick a starting repo or treat this as its own spec rather than silently running `install.sh` against all 5.

**INFRACOST_API_KEY:** not provisioned — genuinely requires the user to sign up (human/browser action), not something the agent can do unilaterally. Asked whether they already have a key or want it deferred.

## 2026-09-03 — real Terraform installed via HashiCorp binary, not apk
`terraform` was never a valid Alpine apk package (BUSL license, not apk-distributed) — this was already broken in the Dockerfile before this session, confirmed live via `apk search -x terraform` (empty) vs `apk search -x opentofu` (found, real package). Fixed by installing Terraform via HashiCorp's official binary release, same pattern as tfsec/kube-score. Kept `opentofu` via apk as-is. Version pinned to 1.16.1 — my first attempt (1.17.0) was wrong, scraped from HTML text on the releases page that wasn't an actual published version; corrected against the authoritative `releases.hashicorp.com/terraform/index.json` with real semver sort, and confirmed by actually downloading the file (HTTP 200, valid zip signature) before touching the Dockerfile again.

## 2026-09-03 — added `-f` (fail-on-HTTP-error) to every raw `curl -o`/`-Lo` download in Dockerfile.sandbox
The wrong-terraform-version bug above only surfaced as a build failure because `unzip` choked on garbage — the `curl -sSLo` that fetched it had no `-f`, so a 404 HTML/XML error page downloaded "successfully" and was silently treated as the real file. Audited the whole file for the same class of bug: 6 more downloads (terraform-docs, polaris, pluto, kubeconform, kube-linter, and the pre-existing sonar-scanner line) had the same gap. All fixed. This is a systemic fix, not just a terraform fix — prevents the same silent-corruption failure mode from recurring on any future version bump of any of these tools.

## 2026-09-03 — removed `npm install -g npm@latest` from Dockerfile.sandbox
Also pre-existing, different bug, same apk-add line: on `node:20-alpine`, "latest" npm (12.x) requires Node >=22, breaks immediately (EBADENGINE). Node 20 already bundles npm 10.8.2, sufficient for every later `npm install -g <tool>` step in the file. Removed rather than pinned to a fake-compatible-sounding version — nothing downstream needs npm >10.

## 2026-09-03 — replaced tfsec's and kube-score's official install scripts with direct binary downloads
tfsec's script is fragile in two independent ways on this image (rate-limited GitHub API call to resolve "latest"; `sha256sum --quiet`, a GNU-only flag busybox doesn't support). kube-score's install.sh no longer exists upstream at all (404 on both `master` and `main`). Rather than patch upstream scripts, switched both to the same direct-pinned-binary pattern already used for gitleaks/osv-scanner/kube-bench elsewhere in the file.

## 2026-09-03 — infracost install switched from `infracost/infracost` to `infracost/cli`
The old repo's own install script says it only supports versions <1.0.0 and points to `infracost/cli` for anything current (now at v2.16.2). Using the correct, actively-maintained repo and its installer.

## 2026-09-03 — added `gcompat` to the sandbox base image
`infracost`'s binary (and, separately, sonar-scanner's bundled JVM — see below) is glibc-linked; Alpine is musl-based. `gcompat` (Alpine's glibc-compat shim) fixed infracost. Confirmed via `readelf -l` (missing `/lib64/ld-linux-x86-64.so.2` interpreter) before adding it, not guessed.

## 2026-09-03 — sonar-scanner's JVM failure left unfixed (scope decision)
`gcompat` isn't sufficient for a full JVM (`libjimage.so` still fails to load) — real glibc or a different scanner distribution would be needed, a materially bigger change than anything else in this pass. Left as a documented, known gap (QUESTIONS.md #20) rather than either silently ignoring it or open-endedly expanding scope to fix a pre-existing tool that isn't one of the 20 new gates this initiative was scoped to deliver.

## 2026-09-03 — CI builds Dockerfile.sandbox fresh instead of pulling a published registry image
Avoids needing a registry-publishing decision (ghcr.io org/auth) to satisfy the "local == CI" hard constraint — both sides build from the same in-repo Dockerfile. Registry publishing left as a future speed optimization only, not a blocker (see QUESTIONS.md item 9).


## 2026-09-02 — claude-auto-retry lives in agents-harness, not infra-platform
Rationale: it's meta-tooling for how Claude Code agents run (session/rate-limit management), not cloud infra. agents-harness already owns autonomous-mode rules (rule 9) and has the install.sh pattern (mirrors `install_snip`). Ansible project was considered and rejected — it would configure a remote server to manage a local CLI session, wrong layer.

## 2026-09-02 — retryMessage forces STATE.md re-read instead of blind "continue"
Rationale: claude-auto-retry's tmux send-keys injection cannot detect special confirmation prompts (upstream limitation) — treating its resume as guaranteed context-perfect is unsafe. Pairing it with the harness's own checkpoint protocol (every 3 steps/15min) makes the imperfect injection safe: worst case the agent re-grounds like a fresh session.

## 2026-09-02 — mid-task checkpoint frequency generalized to every task
Rationale: rule 9's 3-steps/15min checkpoint only applied to autonomous mode — a normal task interrupted mid-flight (rate limit, crash) had no intermediate record, only IN_PROGRESS at start and DONE/FAILED at end. Reused the existing cadence constant instead of introducing a second one. Format/content unchanged (user explicit constraint) — only write frequency increased. Applied to harness-infra.md, harness-dev.md (rules 2 and 5) and task-executor.md (new rule 5b), synced to ~/.claude.

## 2026-09-02 — --remote-control mandatory for all autonomous launches and hard relaunches
Rationale: user follows autonomous runs from mobile. Native Claude Code `--remote-control` flag covers this with no inbound ports / no infra change. claude-auto-retry resumes the *same* process (remote-control persists automatically), but a hard relaunch after a crash creates a genuinely new session — that must explicitly re-add the flag, since crash time is exactly when nobody's at the terminal.
